
## 一、项目详情

### 项目概览

- **项目名称**：CouponX — 分布式优惠券秒杀与抽奖发放平台
- **项目架构**：DDD 领域驱动设计 + 微服务架构 + 前后端分离
- **核心技术**：SpringBoot、MyBatis、MySQL、Redis、RabbitMQ、Dubbo、Nacos、xxl-job、Canal、ElasticSearch
- **项目定位**：支撑优惠券秒杀抢购、差异化抽奖发券、积分兑换、行为返利四大核心业务域，以 Dubbo + Nacos 对外暴露 RPC 标准接口
- **压测数据**：抽奖接口 500~800 TPS / 45~100ms；秒杀接口单机 600+ TPS / P9 80ms 以内

---
### 四大业务模块

#### 1. 优惠券秒杀抢购

用户在活动开始时抢购限量优惠券，核心挑战是瞬时高并发下的库存准确性与系统稳定性。

**完整业务流程**：
1. 活动开始前，运营配置券的库存、限购规则、开抢时间，系统预热数据到 Redis
2. 用户进入活动页，前端展示"可抢 / 已抢完 / 未开始"实时状态
3. 用户点击抢购，入口层令牌桶限流，过滤无效请求
4. Lua 脚本原子校验资格 + 预扣 Redis 库存，防止超卖
5. 下单请求入 RabbitMQ 队列，消费者异步写库生成订单
6. 用户收到"抢购成功"通知，可在订单中心查看券码
7. 支持用户主动取消订单，触发库存回流与链路补偿

**关键设计**：
- 库存全程走 Redis，数据库不参与实时竞争
- 一人一单通过 Redis 分布式锁保障，集群模式下线程安全
- xxl-job 定时对账，修复 Redis 与 DB 的库存差异

---

#### 2. 差异化抽奖发券

通过抽奖方式发放优惠券，支持多种差异化玩法，增加用户参与感与活动趣味性。

**支持的抽奖玩法**：
- **通用抽奖**：按概率随机抽取，所有用户参与
- **黑名单拦截**：指定用户群体不参与抽奖，直接返回兜底奖品
- **人群圈选**：仅特定标签人群（如 VIP、新用户）可参与
- **积分消耗抽奖**：消耗 N 积分后解锁指定范围奖品
- **N 次解锁奖品**：累计抽奖 N 次后才可中某个特定奖品

**完整业务流程**：
1. 运营在后台配置抽奖策略、奖品概率、规则树节点，无需发版
2. 用户触发抽奖（点击 / 积分兑换 / 行为触发）
3. 责任链依次过滤：黑名单 → 人群校验 → 积分门槛
4. 通过校验后执行抽奖算法，O(1) 时间复杂度随机命中奖品
5. 规则树判断抽奖中和后的动作（库存扣减、次数记录、兜底）
6. 异步发放奖品，写入中奖记录，MQ 通知下游

---

#### 3. 积分兑换

用户消费行为积累积分，可用积分兑换优惠券或抽奖资格，构建用户激励闭环。

**完整业务流程**：
1. 用户在积分商城选择要兑换的券种或抽奖次数
2. 系统校验用户积分余额是否充足
3. 生成兑换订单，通过 RabbitMQ 异步通知积分服务扣减积分
4. 积分扣减成功后，发放对应优惠券或增加抽奖次数
5. 兑换记录写库，用户可在明细页查看消费流水
6. xxl-job 定时对账，修复积分扣减成功但券未发放的异常情况

**关键设计**：
- 积分扣减与券发放通过 MQ 解耦，主链路不阻塞
- 消费端以兑换订单 ID 做幂等去重，防止重复发券
- Task 表 + 补偿任务保障积分与券的最终一致性

---

#### 4. 行为返利

用户完成指定行为（签到、消费、分享等）后，系统自动触发返利发放积分或优惠券，驱动用户留存与活跃。

**支持的返利触发行为**：
- **每日签到**：连续签到额外奖励，BitMap 记录签到状态防重复
- **消费返利**：订单完成后按金额比例返积分，MQ 异步触发
- **邀请返利**：成功邀请新用户注册，双方各得奖励
- **活动行为**：参与特定活动（抽奖、分享）触发指定返利规则

**完整业务流程**：
1. 用户行为发生，业务系统发送行为事件到 RabbitMQ
2. 返利服务消费消息，匹配当前生效的返利规则
3. 规则树计算应得返利金额 / 券种
4. 异步写入返利记录，发放积分或优惠券
5. Canal 订阅 binlog 将行为数据同步到 ES，支持用户行为多维分析
6. ZSet 维护店铺 Top 买家榜单，HyperLogLog 统计活动 UV

**关键设计**：
- 返利规则全部库表配置，运营可实时调整，无需重启服务
- 消费端幂等保障同一行为不重复返利
- 行为数据异步同步 ES，支持运营侧圈人、分析、精准触达

### 四大领域模块

#### 1. 抽奖引擎域

![](https://telegraph-image-43w.pages.dev/file/AgACAgUAAyEGAATTNkFKAAPjae8WVG0hNI2oPKucVPl_GdFTk1AAAmoPaxt_BXhXmNukZoqvUasBAAMCAAN5AAM7BA.png)

将抽奖流程抽象为**抽奖前 / 抽奖中 / 抽奖后**三段节点，各节点独立扩展行为动作：

| 设计模式 | 作用 |
|---|---|
| 模板模式 | 定义抽奖流程骨架，约定前/中/后的执行顺序，子类只扩展差异行为 |
| 责任链模式 | 前置过滤：黑名单 → 人群圈选 → 积分门槛校验，命中即返回，避免无效抽奖 |
| 规则树（组合模式） | 对抽奖后动作动态编排（发奖/兜底/锁定），规则节点库表热配置无需重启 |
| 工厂模式 | 统一创建各类抽奖策略实例，对外屏蔽具体实现类 |

**支持玩法**：通用抽奖 / 黑名单拦截 / N次解锁奖品 / 消耗积分指定范围抽奖

**库表设计**（四表拆分）：
- 抽奖策略表：记录策略基本信息
- 策略明细表：记录各奖品的库存、概率、规则 key
- 规则配置表：各规则节点的具体参数
- 规则树动作表：规则树的节点关系与动作配置

**触发器层**：统一抽象四类入口 —— HTTP / RPC / MQ 监听 / 定时任务，所有行为均理解为触发动作

- **MQ 解耦**：RabbitMQ 解耦发券流程、异步调账、行为返利三条链路；消费端以业务唯一键做幂等去重，防止重复消费
- **binlog 同步**：Canal 订阅 MySQL binlog，将用户行为增量数据同步至 ElasticSearch，支持多维聚合查询，耗时较纯 MySQL 降低 60%

## 二、面试问题 · 基础

### Q1：你的项目整体架构是怎么设计的？

**答**：项目采用 DDD 领域驱动设计，分为触发器层、应用层、领域层、基础层四层结构。触发器层统一定义 HTTP / RPC / MQ 监听 / 定时任务四类入口；领域层是核心，包含抽奖、秒杀、积分等独立领域，各领域通过依赖倒置调用基础层的数据库、缓存、外部接口资源；服务间通过 Dubbo + Nacos 进行 RPC 调用与注册发现。

---

### Q2：为什么要用 DDD，和 MVC 有什么区别？

**答**：MVC 是贫血模型，数据库持久化对象容易被当作业务对象使用，多人协作时代码腐化严重。DDD 以领域为核心，通过依赖倒置让领域层只关注业务逻辑，数据库 PO 对象被限定在基础层，天然防止持久化对象污染业务代码。对于抽奖这种规则复杂、频繁迭代的业务，DDD 的可扩展性优势更明显。

---

### Q3：抽奖流程为什么拆成抽奖前/中/后？

**答**：受 Spring/MyBatis 源码设计启发，对一个流程进行节点拆解可以实现松耦合扩展。抽奖中各类需求（黑名单、权重、N次解锁、兜底）天然可以归类到抽奖前（资格过滤）、抽奖中（库存扣减）、抽奖后（兜底奖励/发奖）三个节点。这样新增一种玩法，只需在对应节点扩展一个类，不影响其他流程。

---

### Q4：责任链和规则树分别负责什么，为什么这样分工？

**答**：
- **责任链**：用于抽奖前的单项选择问题，从黑名单 → 权重 → 默认，依次判断走哪种抽奖，命中即返回，适合线性单向的过滤流程
- **规则树（组合模式）**：用于抽奖中和后的复杂交叉流程，例如用户抽了几次、库存是否足够、是否满足解锁条件，这是一个多条件交叉的树形判断，适合用规则树动态编排，支持库表配置节点关系

---

### Q5：缓存穿透、雪崩、击穿分别怎么解决的？

**答**：
- **穿透**：布隆过滤器拦截不存在的 key + 空值缓存双保险
- **雪崩**：随机 TTL 打散过期时间，避免大量 key 同时失效
- **击穿**：双重检测锁（DCL）+ 逻辑过期，热点 key 不设真实过期时间，只有一个线程重建，其余线程返回旧值，重建完成后异步刷新

---

### Q6：Redis 分布式锁在项目里怎么用的？

**答**：主要两处：一是秒杀场景下保障集群模式中一人一单的线程安全，用用户ID+活动ID组合 key，防止同一用户并发抢到多张券；二是 xxl-job 多机部署时的任务抢占，谁先拿到锁谁执行，避免同一条补偿消息被多个节点重复发送。

---

### Q7：Cache Aside 模式写操作的顺序是什么，为什么？

**答**：先更新数据库，再删除缓存。不能先删缓存再更新 DB，因为删除后到 DB 更新完成之前，其他请求会读到旧数据并重新写入缓存，导致脏数据长期存在。也不应该更新缓存而是删除缓存，因为更新缓存在并发写场景下容易产生顺序问题。

---

### Q8：Canal 是做什么的，为什么用它？

**答**：Canal 将自身伪装为 MySQL 从节点，通过 dump 协议订阅 binlog，将数据库的增量变更实时同步到 ElasticSearch。用它是因为分库分表后，聚合查询无法跨库直接 join，通过 Canal 把数据汇聚到 ES，就可以支持多维聚合查询，且对业务代码零侵入。

---

## 三、面试问题 · 实战

### Q1：抽奖库存扣减为什么用 Redis decr 而不是数据库行锁？

**答**：数据库行锁在秒杀场景下，成千上万个请求竞争同一行记录，会导致大量数据库连接进入等待，耗尽连接池后整个服务被拖垮，普通查询也从几十毫秒变成分钟级超时。Redis decr 是原子操作，性能远高于行锁，配合 setnx 分段锁兜底，在保证不超卖的同时，将锁的粒度细化到每个库存编号，接近无锁化设计。

---

### Q2：decr 已经是原子操作了，为什么还要加 setnx 锁？

**答**：因为 Redis 集群模式下，decr 请求可能因网络抖动超时返回，此时 decr 可能已执行也可能未执行，结果不确定，10万次操作可能出现10万零1或不足10万的情况。另外主从切换时，如果主节点的 decr 未同步到从节点就挂掉，incr 值会回退，可能超卖。setnx 加锁是对这种极端情况的兜底，失败直接返回"库存不足"，允许少卖但绝不超卖。

---

### Q3：Redis 库存和数据库最终一致性怎么保障？

**答**：三个手段：
1. 每次 decr 成功后写入 Redis 延迟队列，定时任务趋势更新数据库，控制写库速率
2. Redis 库存耗尽后推送 MQ 消息，更新数据库库存为 0
3. 活动结束后，xxl-job 扫描所有抽奖参与记录，校准最终库存消耗量

---

### Q4：RabbitMQ 消息可靠性怎么保障，消息丢失怎么处理？

**答**：
- **生产端**：发送成功后同步写一条任务记录到数据库，状态标记为"待确认"，MQ 确认回调后更新为"已发送"
- **消费端**：以业务唯一键（如订单ID）做幂等去重，保证重复消费不产生副作用
- **兜底**：xxl-job 定时扫描状态为"待确认"且超时的任务记录，重新触发 MQ 发送，形成补偿闭环

---

### Q5：多机部署时 xxl-job 任务会不会重复执行？

**答**：会有这个风险，解决方案是任务执行前先用 Redis 分布式锁做抢占：多个节点竞争同一个锁，抢到的执行，抢不到的跳过本次；锁设置过期时间，如果抢到锁的节点挂掉，等锁超期后其他节点可以重新抢占；任务执行完释放锁，这样保证同一批任务在同一时刻只有一个节点在处理。

---

### Q6：抽奖接口压测 500~800 TPS，瓶颈在哪里？如何优化？

**答**：主要瓶颈有两处：一是 Dubbo RPC 的跨服务调用链路，层层调用带来网络延迟累加；二是规则树节点判断涉及多次 Redis 查询，如果规则数据未预热，冷启动时延迟较高。优化手段：活动上线前做数据预热，将策略、规则、库存信息全部加载到 Redis；对于可并行的外部查询，用多线程异步并发发起，统一收拢结果，减少串行等待时间。

---

### Q7：如果面试官说"抽奖不是高并发，为什么要用 Redis 抗并发"？

**答**：抽奖在很多场景下确实是高并发的，比如春晚红包抽奖、电商大促中的转盘抽奖、拼多多每次支付完成后的抽奖弹窗，瞬时 TPS 可以很高。即使并发量不到秒杀级别，只要每秒请求超过几百条，多个请求同时竞争数据库同一行库存记录，就会产生大量行锁等待，数据库连接池很快耗尽，一个普通查询也会被拖慢。Redis 扣减的意义不只是"抗并发"，更是将数据库从资源竞争中解放出来，保障整体系统稳定性。

---

### Q8：发奖 MQ 消息重复发送，怎么保证奖品不超发？

**答**：消费端以业务唯一键（奖品订单ID）做幂等校验，消费前先查库是否已存在该订单记录，存在则直接 ack 跳过，不存在才执行发奖写库。写库使用唯一索引兜底，即使并发两条相同消息同时到达，数据库层面也只有一条能写入成功，另一条抛出唯一键冲突后正常 ack，不进入重试。

---

### Q9：分库分表后聚合查询怎么做？

**答**：引入 Canal 订阅 MySQL binlog，将各分库分表的数据增量同步到 ElasticSearch，聚合查询全部走 ES。这样分库分表只承担写入压力，ES 承担查询压力，两者解耦。对于实时性要求更高的场景，可以引入 Flink 做流式计算，从 binlog 数据流中实时计算并写入 ES 或 Redis。

---

### Q10：抽奖 N 次解锁奖品是怎么实现的？

**答**：这是规则树中的一个节点。在抽奖中节点，规则树会查询该用户在当前策略下的历史抽奖次数（存储在 Redis 或数据库），与规则配置表中的解锁阈值比较。如果未达到阈值，该奖品节点返回"不可得"，规则树继续往下走兜底节点；如果达到阈值，正常发奖并重置计数。规则参数全部来自库表，产品可以随时调整解锁次数无需改代码。
