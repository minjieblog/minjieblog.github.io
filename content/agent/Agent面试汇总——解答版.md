## 上海与非智联科技 · Agent 开发实习 · 一面

> 时间：2026.6.25 ｜ 形式：线上视频 ~30min ｜ 结果：待定

### 一、项目深挖（MewCode / ADC Coding Agent）

**1. 你这个项目相当于把 Claude Code 的结构复刻了一遍？（怎么回应原创性质疑）**

- 不是照搬 API，是按 Coding Agent 该有的模块从零自己实现，目的是搞懂 **Agent 内部**怎么决策
	
- 走通了Coding Agent的五层架构（引擎 / 工具 / 交互 / 安全 / 记忆）的核心链路 （多了交互CLI和安全，即权限上的处理）
	
- 和 CC 的差异
	- 商业化
	- 压缩策略
	- 工具数量

---

**2. 你提到两层压缩机制，具体是怎么实现的？**

- **落盘**：大工具结果放到磁盘，不进历史（单结果超50k字符或者一轮工具总和超200k）-> 只留2K预览 + 文件路径
	- 开销很低->完整内容调用ReadFile工具去读那个文件即可
	
- **全量压缩**：每一轮 Loop 检查上轮输入 **token** 是否超过阈值，超过则调用 LLM 生成**对话摘要+边界提示**替换**旧历史**，CLAUDE的做法是上一轮20K+13K这一轮次
	- 原因：落盘不够用，上下文依然接近于爆炸，这个时候需要调用LLM自己来生成一份对话摘要
	  
- **用户主动 compact**：用户主动触发压缩命令
	- 手动compact的安全余量只有3k

---

**3. 压缩具体怎么做的？针对 N 轮对话怎么处理——每轮都压吗？**

- 不是每轮都压：每轮只做「检查」，没超阈值就不动
	
- 超阈值才触发一次摘要：把较早的多轮对话压成一段摘要，保留最近若干轮原文
	
- 工具大结果单独走落盘，不进摘要

---

**4. 怎么判断哪些语义 / 轮次是「重要」的？**

「重要」要拆成**两层**讲，别混成一句「按规则保留」——上次含糊就是没分开：

- **第一层 · 结构性保留（确定性，不需要「判断重要性」）**：
	- 新近度：保留最近若干轮原文
	- tool_use / tool_result **必须成对保留**，不能拆（拆了下一轮 API 直接报错）
	- 系统指令 / CLAUDE.md / Skill 本身精简 → 不压；大工具结果**落盘**，只留 ~2K 预览 + 文件路径
- **第二层 · 语义「重要性」——不靠代码判定，靠摘要 prompt 引导**：
	- 全量压缩时调 LLM 生成摘要，摘要 prompt 里列了 **9 类必须保留的内容**；能确认的是**第 6 项「尽量保留用户消息原文」**（其余按你 prompt 实际内容补：如关键决策与理由、未完成任务 / 待办、关键文件与改动、报错与修复过程）
	- ⚠️ 本质是 **prompt 层的「约束语气」引导，不是硬规则**——模型可能没照做，这正是第 5、6 题「压缩丢关键信息」的根源
- **面试点睛**：结构性保留是**确定性**的、语义重要性是**概率性**的 prompt 引导；拿确定性机制（成对保留、落盘、最近 N 轮）兜住概率性部分，但别夸大成「能精确判定重要性」——这样既准确又踩到 Harness「用确定性兜住不确定性」的点

[[Agent开发面试题#上下文压缩]]

---

**5. 压缩中有没有遇到过「压不好导致输出变差」的情况？具体什么 case？**

- 典型 case：压缩把关键 `tool_result` 丢了 → 模型不知道某工具已执行、拿到什么结果 → 反复调同一个工具，陷入死循环
	
- 因果链很长，AI 自己只会在症状处打补丁，定位很难
	
- 解决：回放 JSONL 日志逐轮对比找根因；压缩时保证 tool_use / tool_result 配对不被截断

---

**6. 这个压缩机制处理不了哪些边界条件？**

- 对话又长又杂、信息密度高时，摘要会丢细节，模型决策变差
	
- Function Calling 配对约束：压缩不能拆散 tool_use / tool_result，否则下一轮 API 直接报错
	
- 摘要本身也要调 LLM，可能再次超限 → 要预留余量 + 分组**重试兜底**

---

**7. 权限拦截是怎么设计的？（几层、每层做什么）**

由内到外五层，任一层 deny 就短路：

1. 危险命令检测：针对 Bash，正则拦 `rm -rf /`、mkfs、fork bomb 等

2. 规则引擎：用户级 / 项目级 / 本地级规则文件，按 Tool 匹配 allow/deny

3. 路径沙箱：文件类工具把路径解析成绝对路径，判断是否落在项目根目录内

4. 权限模式：default / acceptEdits / plan 几种挡位

5. HITL：最外层人工确认兜底

---

**8. 每一层具体的「目的 + 实现」能讲细一点吗？**

- 命令检测：防破坏性 shell 操作，正则黑名单匹配
	
- 规则引擎：让用户 / 项目可配置放行或拒绝，按工具名 + 参数匹配三级规则文件
	
- 路径沙箱：防越权读写项目外文件，绝对路径前缀判断
	
- 权限模式：控制自动化边界（只读 / 自动改 / 只规划）；
	
- HITL：前面没拦住的弹框让人确认

---

**9. 路径沙箱解决什么问题？通过什么方式让文件索引更精确？**

- 解决两件事：① 安全——防止读写项目**根目录**之外的文件；② 定位准确——文件操作统一用**绝对路径**
	
- 做法：把工具传入的相对路径解析成绝对路径，再判断是否在项目根内，不在就拒绝
	
- 绝对路径让 Grep / Glob / Read 定位文件无歧义，不依赖「当前在哪一层」

---

**10. 规则引擎是干什么的？（注意：别和权限模式搞混）**

- 规则引擎是权限**第二层**：读用户级 / 项目级 / 本地级三层规则文件，按 Tool（名字 + 参数）匹配 allow / deny
	
- 作用：让用户和团队把「哪些操作放行、哪些拒绝」写成配置文件，不用每次人工确认
	
- ⚠️ 别和**权限模式**（default / acceptEdits / plan，那是第四层）搞混——上次就是答错在这

---

**11. LLM 适配的协议是通用的吧？多厂商怎么切换？**

- 通用：抽象了统一的 LLM Client 层，对上层屏蔽厂商差异

- 切换厂商只需换 API 配置（base_url / key / model），把各家响应适配成统一的 tool_use / tool_result 结构

- Function Calling 协议各家大同小异，做一层转换即可

---

**12. 记忆怎么管理？存成什么文件 / 什么方式？什么时候被加载？**

先划清边界：**记忆 ≠ 落盘 / 压缩**——落盘、摘要是**上下文 / 执行层**的操作；记忆指的是**跨会话**沉淀的用户偏好、纠正反馈、项目知识。然后分层讲：

- **① 短期记忆 vs 长期记忆**：
  - **短期记忆** = 当前会话的**对话历史 / 工作记忆**，活在上下文窗口里，存对话细节，会话结束即消失（除非持久化）
  - **长期记忆** = **跨会话**有价值的内容，持久化到外部（文件 / json / 向量库），存的是**提炼后的事实 / 偏好**
  - 关键点：**短期记忆里必须完整保留 Function Call 的 `tool_use` / `tool_result`**——否则模型不知道调过什么、拿到什么结果，会**重复调用、配对断裂、上下文不一致**

- **② 长期记忆按两个维度切**（讲清记忆系统的关键）：
  - **作用域**：用户级（`~/`，跨项目偏好，如编码风格 / 命名规范）vs 项目级（`.minicoder/`，只对当前项目，如技术栈 / 架构约定）
  - **来源**：**项目指令文件**（CLAUDE.md / MEWCODE.md，人手写的工程规范，显式）vs **自动记忆**（Agent 从对话自动提取的偏好 / 反馈，隐式）

- **③ 短期怎么转成长期**：在触发条件（重要 / 重复 / 用户明确指定）下，把对话提炼成事实 / 偏好，写进持久化文件（`auto_memory.json` / markdown 记忆文件，`MEMORY.md` 做索引），下次按相关性检索注入

- **存成什么 + 什么时候加载**：文件式（json 或 markdown）；**会话开始 / 第一次调用时注入**，用注入标志位防重复、压缩后重置标志重注（详见第 13 题）

- **冲突处理**：记忆和当前对话冲突时，**以当前对话 / 最新信息为准**，记忆只作背景参考、冲突时降权，必要时向用户确认

[[Agent开发面试题#记忆系统]]（第 20 / 21 / 27 题）｜[[Agent开发面试题#05 Agent 进阶以及实际应用]]（第 111~120 题短 / 长期记忆）

**13. 记忆（用户偏好、项目知识）是在 ReAct 循环的哪一步、什么时机给到模型？**

- 在每轮 Loop 的「拼装上下文」步注入（第一步检查 / 压缩之后）
	
- 注入位置：对话历史开头、环境信息之后；顺序 = 环境信息 → 项目指令（CLAUDE.md）→ 自动记忆 → 一条「已了解」的假装助手消息
	
- 用注入**标志位**防重复，压缩后标志重置、重新注入到摘要后面

---

**14. 上下文压缩发生时，提示词里的「用户问题 / 系统提示词 / 记忆 / CLAUDE.md / 工具技能」这几块分别怎么被处理？**

先给框架:压缩时这几块的「命运」分**三类**——常驻不压 / 被摘要压 / 特殊处理;按提示词三个物理通道（system / tools / messages）对号入座就清楚了。

- **A. 常驻不压（稳定 + 走 Prompt Cache，压缩根本不碰）**
	- **系统提示词**（→ system）：Agent 角色 / 规则 / 输出格式，固定不变
	- **工具定义 + Skill**（→ tools）：工具 schema 相对固定；Skill 本身是精简的指令（不是执行产生的中间内容），也不压
	- **CLAUDE.md（项目指令）**（→ messages 开头注入）：人写的项目约定，精简且要稳定
	- ↑ 这几块放前缀、长期不变，正好命中 prompt cache；压它们反而击穿缓存，得不偿失
- **B. 被摘要压缩的主体**
	- **用户问题 + 对话历史**（→ messages）：压缩的主要对象，较早轮次被 LLM 摘要化
	- ⚠️ 摘要 prompt 明确要求「尽量保留用户消息原文」（9 项必保的第 6 项）——但这是 prompt 层引导、非硬保证（呼应第 4 题）
- **C. 特殊处理（既不是简单常驻，也不是直接进摘要）**
	- **工具大结果**（→ messages 里的 tool_result）：走落盘，历史只留 ~2K 预览 + 路径，不进摘要；模型要完整内容再 ReadFile
	- **记忆**：最容易讲漏的一块——压缩会把旧历史（含之前注入的记忆）换成摘要，记忆可能被一起压没；所以用**注入标志位**：平时注过不重复注，一旦压缩就**重置标志**，下一轮把记忆**重新注入到摘要后面**，保证不丢（见第 13 题）
- **一句话收尾**：稳定的指令类（system / tools / CLAUDE.md / Skill）常驻走 cache、不压；膨胀的对话历史摘要化、但尽量留用户原文；大结果落盘留指针、记忆压完补注——每块按「是否稳定 + 是否膨胀」区别对待，而不是一刀切全压

**16. 用 AI Coding 有什么体验？踩过什么坑？经验总结？**

分三块答:一句话体验 → 核心方法论 → 踩过的坑。

- **一句话体验**:AI 把「写」的成本打下来了,但「想清楚 + 验收」的责任全压回到人身上——用得好靠**流程**,不是靠一句 prompt

- **核心方法论:分阶段 + 分粒度**（最该讲的经验）
	- **分阶段——大任务走三步**（见题库第 33 题）:
		- ① **需求对齐（Chat → Spec）**:先聊清需求边界,让它整理成 spec 文件,确认无误再动手
		- ② **方案设计（Plan Mode）**:进 Plan Mode 只读代码、出实施方案,人确认后再执行
		- ③ **逐步实施（SDD + 小步 commit）**:按任务拆分一步步来,改完一步跑测试 + lint、commit 一步
	- **分粒度——按任务大小给不同投入**（见题库第 34 题）:小活（改名 / 格式）直接做、不纠结 prompt;中等（加功能 / 修 bug）给明确范围 + 验收条件;大活（架构 / 新模块）才上三阶段
	- 一句话:**别对所有任务都写长 prompt,也别对大任务图省事直接开干**

- **踩过的坑**（见题库第 37 题）:
	- **上下文太长会降智**:一个会话干太多事,后面输出质量明显下降 → 每个独立任务 `/clear` 重开
	- **复杂 bug 只会在症状处打补丁**:因果链长的问题（如压缩丢 tool_result 导致死循环）,AI 定位不到根因,得自己**回放 JSONL 日志**逐轮对比
	- **有些活 AI 根本搞不定**:需要跨多层全局推理、或依赖隐性知识（项目背景 / 历史决策）的,只能自己动手（如手写流式 parser 状态机）,让 AI 补边界和测试

## 上海张量记忆 · Agent 开发实习 · 一面

> 时间：2026.6.30 ｜ 形式：线上视频 ~30min ｜ 结果：待定 ｜ 本场重点：**Claude Code 源码 + 上下文工程**（问得很细，机制层深挖）

> 纯背景闲聊题（自我介绍、年级、本科为何选数据科学、能实习多久、研一课程等）略，这里只收技术 / 项目题。

### 一、项目 & Claude Code 源码

**1. 简单介绍一下这个项目（功能 + 五层架构 + 上下文 + 权限 + multi-agent）**

- 定位：独立开发的**终端 AI 编程助手**（见题库第 1 题）
- 功能：用户用自然语言下指令 → Agent 自主**读代码 / 改文件 / 跑命令**，全程自主、不用盯每一步
- **五层架构**（见题库第 5 题）：引擎层（LLM Client + Agent Loop）→ 工具层（内置工具 + MCP）→ 交互层（CLI + Skill）→ 安全层（危险命令检测 + 路径沙箱 + HITL）→ 记忆层（持久化 + 上下文压缩）
- 三个特色：**多厂商 API** 一键切换、完整**五层权限**、**两层上下文压缩**，外加**多 Agent 并行**（Coordinator + Worker，Worktree 隔离 + 邮箱异步通信）
- 收尾一句：目标是从零走通 coding agent **每一层的核心链路**，把黑盒拆开看清楚

---

**2. 为什么做 coding agent？这不就是照着 Claude Code 复刻的吗？（动机 + 原创性质疑）**

- 动机：每天在用 Claude Code，但它像个**黑盒**——想搞清楚 Agent 内部到底怎么决策，就自己从零造了一个（见题库第 1 题）
- 为什么偏偏是 coding agent：它把 Agent 的核心能力——**多步规划 / 工具调用 / 上下文管理 / 权限控制**——全逼出来了，是理解 Agent 最好的载体
- 回应「复刻」：不是照搬 API，是**按模块从零实现**；和 CC 的核心差异（见题库第 28 题）——定位（走通每层 vs 商业级生态）、压缩策略（我 3 层 vs CC 五六层多粒度）、工具数量（8 核心 + MCP vs 50+）
- ⚠️ 和《与非智联》第 1 题是同一类质疑，用「从零实现 + 说得出差异点」正面接，别回避

---

**3. 讲讲 Claude Code 源码设计上吸引你的几个亮点？**

- **权限做在工具层**而非 prompt 层：plan mode 直接禁写 / 禁执行工具（见第 9 题）
- **上下文工程**：稳定前缀走 prompt cache、动态信息 system-reminder 注入、阈值触发摘要压缩（见第 4~8 题）

### 二、上下文工程（本场重点拷打区）

**4. Claude Code 在 Context Engineering 上是怎么设计的？（总述）**

- 一句话：**让稳定的东西一直稳定、让易变的东西不污染前缀、逼近窗口才压缩**
- 三个抓手：① 稳定前缀（system prompt + 工具定义）走 prompt cache；② 动态信息（时间、提醒）用 system-reminder 放靠后，不破坏缓存前缀；③ 接近模型窗口上限时对历史做摘要压缩，指令类内容不压

---

**5. 200K 上下文是写死 / 绑定的吗？不同模型不一样，为什么只支持 200K？**

- **不是 Claude Code 写死的**：200K 是 **Claude 模型本身的 context window**，harness 只是读运行时模型的窗口大小
- 压缩阈值按**当前模型窗口动态算**：换成 1M 窗口的模型，阈值就跟着抬高——不假设固定值
- ⚠️ 说 1M 时别说错：**1M 是 Sonnet 的 beta 特性，不是 Opus**；最新 Opus 是 4.8（没有「Opus 4.6」，4.6 是 Sonnet）
- 一句话：「200K 是模型的窗口，Claude Code 按运行时模型窗口动态设压缩阈值，没把 200K 焊死在代码里」
- ⚠️ 上次答成「适中方案」，没答到「这是模型属性、不是 harness 写死」这个点

---

**6. 上下文由哪几部分构成？怎么保证 KV cache / prompt cache 命中率？**

- 核心是 **prefix caching（前缀缓存）**：缓存的是请求**前缀**，任何一个 token 变了，从那往后的缓存全失效
- 稳定前缀走缓存：system prompt、工具定义放最前、长期不变 → 每次命中 cache read
- 动态信息往后放、用 **system-reminder** 注入：时间 / 提醒这类易变内容混进前面会击穿缓存，所以放靠后
- TTL：Anthropic prompt cache 默认 **5 分钟**（有 1 小时扩展档），超时要重写
- **压缩会击穿缓存**：compaction 重写了历史 → 前缀变了 → 下一次全量 uncached，又贵又慢 → 所以不能频繁压缩
- 加分点：只追加、不改前面 → 稳定前缀继续 cache read，只有新增后缀 cache write

---

**7. 调用 LLM 时，哪些上下文常驻？哪些在触及上限时被压缩？（分层讲）**

- **基本常驻、不压**：system prompt、工具定义、CLAUDE.md（项目指令）、记忆、Skill 元数据——本身精简且静态，放前缀，还能走 cache
- **会被压缩**：历史对话（用户 / 助手轮次、tool_result、大文件读取输出）——真正膨胀的是这块
- 关键区分：CLAUDE.md / Skill 是「指令类」常驻内容，不参与摘要；膨胀的是对话历史 + 工具结果
- ⚠️ 上次答成「落盘 + 截前 1/5」是没分层，这次按「指令类常驻 vs 历史摘要压缩」讲

---

**8. 你的滚动压缩策略是什么？是保留最近 5 轮吗？**

- **不是固定 N 轮**，是**两层 + 阈值触发**（对齐你项目《上下文压缩》的说法）：
  - **① 落盘**：大工具结果（单结果 >50K 字符 / 一轮工具总和 >200K）写到磁盘，历史里只留 ~2K 预览 + 文件路径，模型要完整内容再调 ReadFile 去读
  - **② 全量摘要压缩**：每轮检查上轮输入 token，超阈值就调 LLM 生成「摘要 + 边界提示」替换旧历史（你项目里 ~80% 触发、预留 20K 压缩空间 + 13K 当轮 buffer）

- 一句话：「按 token 阈值触发的分级压缩（落盘 + 摘要），不是固定轮数的滑窗」
- 边界 case：压缩丢了关键 tool_result → 模型不知道工具已执行 / 拿到什么结果 → 反复调同一个工具（备好这个具体 case，见本文《与非智联》第 5~6 题）

### 一、概念题

**1. 什么是 MCP？你调用过吗？自己写过 MCP server 吗？**

- **定义**：MCP（Model Context Protocol）是 Anthropic 提出的**开放协议**，标准化「Agent / LLM 应用 ↔ 外部工具、数据源、服务」的连接方式——相当于给 AI 应用接外部能力的「**USB-C 接口**」。
- **核心价值**：把 **M 个应用 × N 个工具**的重复对接，从 **M×N 降到 M+N**——每个工具只实现一次 MCP server，任何 MCP client（Claude Code / Cursor…）都能直接用。⚠️ 不是「减少大模型调用工具的频次」（上次答偏在这）。
- **架构**：Host（如 Claude Code）内含 **MCP Client**，通过 **stdio / HTTP(SSE)** 连到 **MCP Server**；Server 暴露三类能力——**Tools**（可调用函数）、**Resources**（可读数据 / 上下文）、**Prompts**（预置提示模板）。
- **诚实作答**：项目里**集成 / 调用过** MCP server，自己**没从零写过**。要写的话：用官方 SDK 注册 tools / resources 的 handler，跑成一个进程供 client 连接。

---

**2. MCP 和 Function Calling 有什么区别？**

- 两者**不是一个层级**，是**互补**关系：
- **Function Calling = 模型侧的调用约定**：模型拿到工具 schema（name / description / input_schema），推理时输出结构化的 `tool_use`（「我要调 X、参数 Y」），调用方执行后把 `tool_result` 回喂。解决「**模型怎么表达要调工具**」。
- **MCP = 工具侧的接入标准**：解决「**外部工具 / 数据源怎么以统一方式接到任意 Agent**」。MCP server 暴露的 tools，最终仍是通过 Function Calling 交给模型去调。
- **一句话**：FC 是「模型 ↔ 调用方」的结构化通信格式；MCP 是「Agent ↔ 外部工具生态」的接入 / 复用标准。**FC 决定模型怎么发起调用，MCP 决定工具怎么被发现和复用**。

---

**3. 什么是 git worktree？（在 multi-agent 里的作用）**

- **定义**：git worktree 是 Git 原生功能，允许**同一个仓库**同时挂载**多个工作目录**，每个 worktree 检出**不同分支**，**共享同一个 `.git` 对象库**但工作区文件互相隔离。
- **在 multi-agent 里的作用**：给每个并行 worker 分一个独立 worktree（独立分支 + 独立目录），worker 之间改动**互不踩踏**、可真正并行，最后再合并。
- ⚠️ 上次直接说「让 worker 在独立环境工作」，方向对但没讲清 worktree 本身是「一库多工作树、共享 `.git`」。

---

**4. 多智能体协作好在哪？**

- **任务拆解**：单 agent 上下文 / 职责单一；复杂任务拆给多个专职 worker，协作效果优于硬塞给一个 agent。
- **上下文隔离**：每个子 agent 独立上下文窗口，避免相互污染、也省 token。
- **并行**：无依赖的子任务并行跑，提速。
- **我的实现**：参考 Claude Code 的**非去中心化**做法——一个 **Coordinator** 拆分 + 分发任务给多个 **Worker**，Worker 各自独立 **worktree** 隔离、通过**邮箱异步通信**。
- ⚠️ 诚实：实测 multi-agent 效果不一定稳超单 agent（拆解 / 汇总带来额外开销），可据实讲。

---

**5. RAG 用什么向量数据库？（我项目没做 RAG，怎么答不露怯）**

- **诚实**：我的 coding agent **没用向量 RAG**——代码检索走的是**实时 grep / glob + 读文件**，不是向量召回。
- 但要能讲清 **RAG 是什么**：检索增强生成——外部知识**切块 → embedding → 存向量库 → query 时按向量相似度召回 top-k → 拼进 prompt**。
- **常见向量库**：FAISS（本地库）、Milvus、Chroma、Qdrant、pgvector、Pinecone（云）。
- **加分点**：能说清「**coding agent 为什么不用向量 RAG**」——代码要的是**精确匹配**（grep / AST）而非语义近似；Claude Code 的记忆检索也是 **LLM 判相关性 + 层级文件加载**，不是向量搜索。

### 二、手撕算法（本场最大失分点）

**6. Top K Frequent Words（LeetCode 692）**

> 给一个单词列表 `words` 和整数 `k`，返回出现次数最多的 `k` 个单词；频率相同按**字典序升序**。面试官发的是 C++ 函数签名、要求关 AI 补全现写。

**思路**：哈希计数 → 按（频率降序、字典序升序）取前 k。两种实现：

**解法一 · 排序，O(n log n)**

```cpp
vector<string> topKFrequent(vector<string>& words, int k) {
    unordered_map<string,int> cnt;
    for (auto& w : words) cnt[w]++;
    vector<string> uniq;
    for (auto& [w, c] : cnt) uniq.push_back(w);
    sort(uniq.begin(), uniq.end(), [&](const string& a, const string& b){
        if (cnt[a] != cnt[b]) return cnt[a] > cnt[b];  // 频率高在前
        return a < b;                                   // 频率同则字典序小在前
    });
    return vector<string>(uniq.begin(), uniq.begin() + k);
}
```

**解法二 · 小顶堆，O(n log k)（更优）**

```cpp
vector<string> topKFrequent(vector<string>& words, int k) {
    unordered_map<string,int> cnt;
    for (auto& w : words) cnt[w]++;
    // 堆顶放「最该被淘汰」的：频率小的先出；频率相同，字典序大的先出
    auto cmp = [](const pair<string,int>& a, const pair<string,int>& b){
        if (a.second != b.second) return a.second > b.second;  // 频率高 = 更该留 = 靠堆底
        return a.first < b.first;                              // 频率同：字典序小 = 更该留
    };
    priority_queue<pair<string,int>, vector<pair<string,int>>, decltype(cmp)> pq(cmp);
    for (auto& [w, c] : cnt) {
        pq.push({w, c});
        if ((int)pq.size() > k) pq.pop();   // 淘汰堆顶（最该被淘汰的）
    }
    vector<string> res(k);
    for (int i = k - 1; i >= 0; --i) { res[i] = pq.top().first; pq.pop(); }  // 从差到好倒着填
    return res;
}
```

**Python 版（备用）**

```python
import heapq
from collections import Counter

def topKFrequent(words, k):
    cnt = Counter(words)
    # 频率降序 → 用负频率；字典序升序 → 直接用单词；nsmallest 按 key 升序取前 k
    return heapq.nsmallest(k, cnt.keys(), key=lambda w: (-cnt[w], w))
```

**复杂度**：解法一 O(n log n)、解法二 O(n log k)（n = 去重后单词数）。

**复盘教训**：
- ❌ 本地没配 C++ 编译环境 → 现场没法验证编译。**必须提前配好 g++ / MinGW（或 VSCode + Code Runner）**。
- ❌ STL 裸写生疏（`unordered_map` 遍历、`priority_queue` 自定义比较、`sort` lambda）→ 依赖 AI 补全的短板暴露。**这几个模板要背到肌肉记忆**。
- ⚠️ 只想到排序 O(n log n)，没提堆 O(n log k)——Top-K 问题要条件反射想到堆。

**3. 关于自己编写 Skill，你有了解吗？**

按「是什么 → 四件套 → 渐进加载 → 执行模式 → 评测」讲成一个小体系，比一句「打包工作流」完整得多。

- **是什么 + 为什么用它**：Skill 是把**领域知识 / 工作流**打包成一个「能力包」，让 Agent **按需加载**。价值在于能力按需加载、**不占满上下文**、可复用、可组合。按用途分两类——**工具 Skill**（封装一项具体操作能力）和**产品 Skill**（封装某产品 / 领域的方法论、规范、输出模板，偏业务任务）。

- **四件套结构**：
  - **SKILL.md**：技能的工作手册——带 name / description 的 frontmatter + 正文，说明**何时用 + 步骤 + 规范**
  - **references/**：参考资料，如 API doc、`style-guide.md`、`troubleshooting.md`
  - **scripts/**：可执行脚本，如解析 PDF / 发邮件 / 查天气的 python / shell
  - **assets/**：模板 / 静态资源，如 PPT 模板、logo、字体、图片

- **渐进式加载（三层披露）**——最能体现「懂上下文工程」：
  - **① 元数据层**：只有 name + description，**常驻**上下文、占用极小，供模型判断「该不该用这个 Skill」
  - **② 指令主体层**：命中后才加载 SKILL.md 正文
  - **③ 附加资源层**：真正用到才去读 scripts / references
  - 效果：一个 Skill 从「一次性塞 ~16K token」降到常驻约 **500 token**——用渐进式披露把上下文占用压到最低（和 MCP 工具延迟加载省 token 是同一思路）

- **两种执行模式**：
  - **inline**：Skill 的 prompt 注入当前会话，主 Agent 带着继续跑——轻量、和当前任务连贯
  - **fork**：开独立子 Agent 执行，有自己的对话历史 + 过滤过的工具集——重、独立、跑完**不污染主上下文**（和 Multi-Agent 上下文隔离同思路）

- **怎么评测一个 Skill 好不好**：核心看「**该用时有没有被正确触发、有没有用对**」；指标 = 触发准确率、任务成功率、对比有无 Skill 的效果；收集 bad case 反过来迭代 description。**description 直接决定能否被触发，是 Skill 最关键的一环。**

- **skill_creator**：有一个「用来创建 Skill 的 Skill」——引导描述需求、自动生成 SKILL.md 和目录结构，降低手写门槛。

- **可举的自建 Skill**：代码审查、提交规范、项目专用查询 / 部署流程——把「重复工作流 + 团队规范」固化成 Skill，再配合评测迭代。

### 二、Agent 概念 & 项目深挖（技术面试官）

**6. 你写 MewCode，是觉得 Claude Code 哪点不好用去写，还是学习用途？写的过程中发现什么问题、有什么想法？**

- **动机**（见题库第 1 题）：不是嫌它不好用，是**每天在用、但它像个黑盒**——想搞清楚 Agent 内部怎么决策，就从零造一个。而且 **coding agent 是最通用的 Agent 形态**：只要任务能转成「改代码」，就能用它做，值得吃透。
- **发现的两个真问题**（这题答得越具体越好，我实际答的就是这两个）：
  - **① 上下文压缩的边界 case**：压缩时不小心把某个工具的 `tool_result` 压没了 → 下一轮 ① Function Calling 要求 `tool_use` / `tool_result` **成对匹配**，缺一个直接中断报错；② prompt cache 也命不中。症状是**模型反复调同一个工具**，因果链很长、难定位（见《与非智联》第 5~6 题）。
  - **② multi-agent 的困惑**：理论上复杂任务拆给多个 Agent 并行、效果应更好，但**实测单 Agent 反而更稳**——不确定是我拆解 / 汇总方案不够好，还是和底层模型能力强相关（诚实抛出这个开放问题，反而显得真做过）。

**7. 介绍几种常见的 Agent 范式，讲讲它们的结构？**

（4 种，每种一句「是什么 + 结构 + 取舍」）

- **ReAct**（Reasoning + Acting）：思考 → 行动 → 观察 循环，最主流；结构上每步都「先推理再调工具再看结果」。灵活，但每步都推理、**token 消耗大**。
- **Plan-and-Execute**：先把任务**拆成完整计划**，再逐步执行；相对省 token（规划阶段不反复试错写文件）。⚠️ 别说成「只推理一次」——规划阶段照样多轮读文件。
- **Reflection / Reflexion**：做完再**自我检查**——额外引入一个 Agent / 一轮调用去评估上一轮结果好坏、给反馈重试；代价是 **token 成本翻倍**（我项目里用测试框架替代显式反思）。
- **Multi-Agent（Coordinator + Worker）**：Coordinator 拆分 + 派活，Worker 在各自独立 **Worktree** 里并行干活、汇总结果；适合可拆分且单任务耗时明显的场景。

**8. Function Calling 和 MCP 有什么区别？**

> 与《平行时空》第 2 题同题，口径一致，别再答成「MCP 减少调用频次」。

- 两者**不是一个层级、是互补**：
- **Function Calling = 模型侧的调用约定**：模型拿到工具 schema（name / description / input_schema），推理时输出结构化 `tool_use`（「我要调 X、参数 Y」），调用方执行后把 `tool_result` 回喂。解决「**模型怎么表达要调工具**」。
- **MCP = 工具侧的接入标准**：Anthropic 提出的开放协议，标准化「Agent ↔ 外部工具 / 数据源」的连接，把 **M×N 降到 M+N**；MCP server 暴露的 tools，最终仍通过 Function Calling 交给模型调。
- **一句话**：FC 决定**模型怎么发起调用**，MCP 决定**工具怎么被发现和复用**。

[[Agent开发面试题#04 MCP / Function Calling]]

**9. MCP 和 Skill 有什么区别？什么时候用 MCP，什么时候用 Skill？各自特点？**

- **一句话切开**：**MCP 给「能力」，Skill 给「方法」**——MCP 负责**连接外部工具 / 数据**（连接协议），Skill 负责**注入知识与流程**（教模型怎么把工具组合起来干活）。
- **MCP（连接协议）**：解决「Agent 从哪接到外部工具 / 数据源」，把工具放独立进程 / 服务、配置即接入；特点——标准化接入、跨应用复用，本质是给模型**多一个可调用的工具**。
- **Skill（知识 / 流程封装）**：解决「一类任务该按什么步骤、用哪些工具做」，打包的是 SKILL.md + 脚本 / 参考资料，渐进式按需加载；特点——**本身不是工具**，是「说明书 / 工作流」，指导模型怎么干活。
- **上下文管理的本质差异**（关键区分点）：MCP 的工具 schema 默认**常驻**上下文（注册了就占 token，工具一多挤占窗口，所以要配「延迟加载」）；Skill 是**渐进式披露**，元数据常驻、正文用到才加载（16K → ~500 token）。
- **什么时候用哪个**：
  - 要接**一个新的外部能力**（查数据库、连内部 RAG、调某 API）→ **MCP**
  - 要固化**一套做事的方法 / 规范流程**（写 PR 的标准步骤、按团队规范生成组件）→ **Skill**
  - 工具很多 → MCP + 延迟加载；流程 / 知识很重 → Skill；两者常**混合**：MCP 接上能力，Skill 教模型「什么时候、按什么顺序」用
- **三者的分层关系收尾**：FC 是地基（怎么通信）、MCP 是标准插座（从哪接工具）、Skill 是说明书（教模型组合工具干活）——**分层、互补的混合架构，不是竞争**。

**10. 说一下 RAG 的完整流程？**

- **离线（建库）**：文档加载 → **分块 Chunking**（按段 / 按页 / 重叠切）→ **Embedding 向量化** → 存入**向量数据库**。
- **在线（问答）**：用户 Query →（可选 **Query 改写**，指代消解 / 补全）→ 向量化 → **检索 Top-N**（常配 BM25 做混合检索）→ **Re-rank 重排**（Cross-Encoder 精排）→ 取 Top-K 拼进 prompt → **LLM 生成**（带引用溯源）。
- **一句话**：检索 + 重排决定上下文质量，生成决定表达；「garbage in garbage out」，**检索质量是上限**。

**11. 你刚讲的是 workflow 里的 RAG，在 Agent 里 RAG 一般怎么用？（第一次没检索到想要的怎么办）** ⭐ 本场关键追问，上次没接住

- **区别在「谁决定检索、检索几次」**：
  - **Workflow RAG**：检索是**写死的一步**——query 进来只检索一次，拼 prompt 就生成；第一次召回不好**没有补救**。
  - **Agentic RAG**：把「检索」**封装成一个工具**，交给 Agent 在 **ReAct 循环**里**自主调用**——Agent 自己判断要不要检索、检索什么、结果够不够；不够就**改写 query 再检索一次**，多轮迭代直到信息足够再回答。
- **面试官原话对齐**：「RAG 整个封装成一个工具，让 Agent 按条件去调用；不满足条件就继续调用工具，可能调好几次」。
- **好处**：① 多轮迭代召回、能自我纠错（第一次不对就换关键词再来）；② 能分解复杂问题做**多跳检索**；③ 能和别的工具（grep / 读文件 / 调 API）组合使用。
- **一句话**：Workflow 的 RAG 是「固定管道里的一步」，Agent 的 RAG 是「模型能反复调、能纠错的一个工具」。

[[Agent开发面试题#03 RAG]]

**12. 你看过 Claude Code 代码，它里面有没有用 RAG 检索？**

- **没有向量 RAG**——Claude Code **不建向量索引、不做向量召回**。
- 代码检索走的是**实时的 grep / glob + 读文件**：模型直接根据对代码库的理解推理关键词去搜。
- **记忆检索**也不是向量搜索，而是 **LLM 判相关性 + 层级文件加载**（CLAUDE.md 从当前目录层层向上加载；auto memory 用 LLM 读 frontmatter 判断相关性）。
- **为什么代码不用向量 RAG**：代码要的是**精确匹配**（函数名 / 变量名 / 报错串），grep 正则天然更准；向量召回是「语义近似」，反而不适合精确定位。

**13. Claude Code 怎么逐步定位一个代码块？比如某个文件没改，怎么定位到代码在多少行？** ⭐ 上次没讲清

- **三个工具配合**：**Grep**（ripgrep，正则搜内容）+ **Glob**（文件名 / 路径匹配）+ **Read**（读文件）。
- **搜索策略由模型自主决定**：根据需求推理关键词 → 搜不到就调整关键词多轮迭代，直到定位。
- **「多少行」从哪来**：Grep 返回**匹配行的行号**，Read 返回的是**带行号的内容**（`cat -n` 格式）——所以模型能精确说出「在第几行」，并据此调 EditFile 精确改那一段。
- **大仓库效率**：瓶颈不在搜索速度（ripgrep 扫百万行几百毫秒），而在模型**选关键词的 LLM 调用次数**；好处是**零预处理、任何语言通用**。
- **MewCode 实现**：标准库写了简化版 GrepTool，思路一致，实测两三轮基本能定位到目标代码。

**18. 你觉得什么时候该 compact，什么时候不该？**

- **我平时的判断**：窗口还想接着用、但发现 Claude「变笨了」/ 上下文太满时压一次；或者中途说了些没用的信息想清掉。

  - **compact 可带重点**：`/compact <要总结的重点>`，让它围绕你关心的点去压。
  - **进阶技巧**：基于当前进度「分身」出另一个窗口去做另一件事；还能接外部 MCP 交互式配置。
- **什么时候别乱压**：任务还在推进、信息都还有用时别压——**压缩会击穿 prompt cache（前缀变了全失效）**，还可能**丢关键 tool_result**；不同独立任务之间该用 **`/clear`** 而不是 compact。

**2. 用户输入一个具体功能后，从 AI 接到输入到完成整个代码生成，怎么一步一步实现的？**（⭐ 本场重头，把 Agent Loop 讲成清晰的五步）

- **会话首次加载**：启动时先加载 Skill、项目指令文件（CLAUDE.md / 工作目录约束）、用户约束、长期记忆——这些是「背景」，一次性注入到上下文最前面。
- **然后进入 ReAct 循环，每一轮五步**：
  1. **检查上下文 → 判断是否压缩**：把本轮的对话历史 + 工具结果 + 记忆加起来算 token，超阈值就触发压缩（落盘 + 摘要两层）
  2. **拼装输入（三个物理通道）**：`system`（角色 / 规则 / 输出格式）+ `tools`（每个工具的 name / description / input_schema）+ `messages`（历轮用户消息、模型回复、`tool_use` / `tool_result`，开头还有环境信息 / 项目指令 / 记忆）
  3. **调 LLM → 判断有没有工具调用**：模型在窗口里读到需要的内容后，自主决定要不要调工具
  4. **执行工具 → 结果拼回历史**：有 `tool_use` 就执行，把 `tool_result` 拼进 `messages`，进入下一轮（可并行的只读工具分批并发）
  5. **判断终止**：靠 **Function Calling 协议**——这一轮模型**没有再返回 `tool_use`** 就说明任务完成、跳出循环；另有 maxTurns 硬上限兜底防死循环
- **加分细节**：模型还在流式输出时，前面已完成的 `tool_use` 就能并行执行（Streaming Tool Execution）；用**循环不用递归**——长任务几十上百轮，递归会栈溢出，循环内存恒定、也方便断点恢复。

**3. 你说会提前写好一些 Skill 技能包，举几个例子？**

- **典型例子**：`review`（代码审查）、`test`（跑测试）、提交规范等——把「重复工作流 + 团队规范」固化下来。
- **两种执行模式**（举 review 说明最清楚）：
  - **inline**：Skill 的 prompt 注入当前会话，主 Agent 带着继续跑——轻量、和当前任务连贯。
  - **fork**：开独立子 Agent 执行，**不接主上下文窗口**，单独做完这步 review 再把结果带回来——重、独立、跑完不污染主上下文。
- **一句话取舍**：轻量、想和当前任务连贯 → inline；重、想隔离上下文（review / 大调研）→ fork。

**4. 这些 Skill 一般有哪些类型？**（分三个维度讲，比只说「组织方式」有层次）

- **① 按用途分**（最该先说）：
  - **工具 Skill**：封装一项具体操作能力（如查询、解析、部署）
  - **产品 Skill**：封装某产品 / 领域的方法论、规范、输出模板，偏业务任务
- **② 按来源层级分**：项目级（`.minicoder/skills`，随仓库走、团队共享）> 用户级（`~/`，个人跨项目）> 内置（打包进二进制、随程序分发）——优先级由高到低
- **③ 按组织形式分**：单个 markdown 文件组织的轻量 Skill vs 一个目录组织的完整 Skill（SKILL.md + references / scripts / assets 四件套）
- 我的实现里主要按**来源层级 + 组织形式**落地（项目级 / 用户级 / 内置，markdown 单文件 / 目录两种组织）；讲的时候先给「用途」维度更容易让面试官 get 到。

**5. 项目里提到跨会话的记忆系统，这个怎么设计的？**（记忆主体；面试里后续被连环追问作用域 / 冲突，见第 6~8 题）

先划清边界：**记忆 ≠ 落盘 / 压缩**——落盘、摘要是**上下文 / 执行层**操作；记忆指的是**跨会话**沉淀的用户偏好、纠正反馈、项目知识。然后分层讲：

- **① 短期记忆 vs 长期记忆**：
  - **短期记忆** = 当前会话的对话历史 / 工作记忆，活在上下文窗口里（≈ 200K，参考 Claude Code），存对话细节，会话结束即消失
  - **长期记忆** = 跨会话有价值的内容，持久化到外部（文件 / json / 向量库），存**提炼后的事实 / 偏好**
  - 关键点：**短期记忆里必须完整保留 `tool_use` / `tool_result`**——否则模型不知道调过什么、拿到什么结果，会重复调用、配对断裂
- **② 长期记忆按两个维度切**：
  - **作用域**：用户级（`~/`，跨项目偏好，如编码风格 / 命名规范）vs 项目级（`.minicoder/`，只对当前项目，如技术栈 / 架构约定）
  - **来源**：项目指令文件（CLAUDE.md，人手写的工程规范，显式）vs 自动记忆（Agent 从对话自动提取的偏好 / 反馈，隐式）
- **③ 短期怎么转长期**：触发条件（重要 / 重复 / 用户指定）下把对话提炼成事实 / 偏好，写进持久化文件（`auto_memory.json` / markdown，`MEMORY.md` 做索引），下次按相关性检索注入
- **④ 什么时候注入**：会话开始 / 第一次调用时注入到对话历史开头（环境信息 → 项目指令 → 自动记忆 → 一条「已了解」的伪助手消息），用标志位防重复、压缩后重置标志重注
- **⑤ 冲突处理**：记忆和当前对话冲突时以当前对话为准，记忆只作背景参考、冲突时降权

**6. 一般 AI 编程工具新功能就新开对话了，你为什么还要跨会话做记忆？**

- 新会话上下文是全新的、之前的对话细节都丢了；但有些东西需要**跨会话延续**，不该每次重新交代：
  - **用户偏好**：编码风格、命名规范
  - **项目约定**：技术栈、架构、团队开发流程
  - **纠正反馈**：用户明确说过「这样设计更好」这类反馈
- 记忆的价值 = 把这些**沉淀下来**，新会话开始时注入回去，让 Agent「记得住你是谁、这个项目什么规矩」。
- 来源两类：人写的项目指令文件（CLAUDE.md）+ Agent 从对话**自动提取**的偏好（如用户反馈自动存进用户级记忆）。

**7. 做完一个项目后，新开一个完全不同技术栈的新项目，这套跨会话记忆还生效吗？**（面试官想听「记忆跟着项目目录走」）

- 关键：记忆**按作用域分层**，不是一锅端全带过去——
  - **项目级记忆**（`.minicoder/`，**跟着项目目录走**）：技术栈 / 架构 / 团队流程——**只在本项目目录生效**，换新项目自然不加载，不会污染
  - **用户级记忆**（`~/`，跨项目）：编码风格 / 命名规范 / 个人偏好——这些**才会跨项目通用**，因为和具体技术栈无关
- 所以「换了完全不同技术栈的新项目」→ 旧项目的**项目级记忆不会带过去**（本来就跟目录走），只有**用户级通用偏好**延续，而这类偏好跨栈也适用、不构成污染。
- ⚠️ 别答成「会污染上下文」——面试官要的就是「按作用域分层、项目级跟目录走」这个点。

**8. 同一个项目里，之前跟 AI 聊的想法后面变了；新开会话后 Agent 还会去读旧会话的记忆吗？**（记忆一致性 / 冲突）

- 先分清两个东西：**旧会话的对话历史** ≠ **持久化的记忆**——
  - 新开会话**不会**把上一条具体会话的完整对话历史加载进来（那是短期记忆，随会话结束就没了）
  - 新会话加载的是**持久化的通用记忆**（用户级 / 项目级的偏好、约定）
- 冲突处理（题库第 120 题）：记忆只作**背景参考**，和当前对话冲突时**以当前对话 / 最新信息为准**，把旧记忆**降权**，必要时向用户确认。
- 工程兜底：Agent 提取记忆时本身会筛选「哪些该沉淀到通用目录」，过时 / 被推翻的偏好可以**覆盖更新**，而不是无脑叠加，避免旧想法一直污染。

**9. Git 基本功：切分支 / 提交新功能 / 解决代码冲突分别用什么命令？**（本场失分点，必须能脱离 AI 敲出来）

- **切分支**：`git branch <name>` 建分支；`git checkout <name>` / `git switch <name>` 切换；一步建+切 `git checkout -b <name>`（或 `git switch -c <name>`）
- **提交一个新功能**：`git add <file>`（或 `git add .`）→ `git commit -m "msg"` →（推远端）`git push`
- **解决代码冲突（完整流，别只说"看 diff"）**：
  1. `git merge <branch>`（或 `git pull` / `git rebase`）触发冲突
  2. Git 在冲突文件里标出 `<<<<<<<` / `=======` / `>>>>>>>`，手动改成想保留的内容
  3. `git add <已解决的文件>` 标记冲突已解决
  4. `git commit` 完成（merge 会生成一个 merge commit）
- 辅助：`git status` 看哪些文件冲突、`git diff` 看差异、`git merge --abort` 放弃这次合并

**10. 反问：agent 开发和传统开发的差别？给我在这个领域的建议？**（面试官的回答，记下来当认知）

- 面试官观点：agent 开发**今年年初才火**、**没有统一标准**，框架 / 架构不断出新、老框架不断被淘汰；要做只能**不断学新技术、钻底层代码、去 GitHub 扒别人的代码**。传统开发则是主流框架已固定、教程教材一大堆，能照着系统学。
- → 对我的启示：这个方向吃「持续学习 + 读源码」的能力，简历 / 面试里要体现「我一直在追新、读过 XX 源码」，而不是只会用现成工具。
